# 部署与运维（Operations）

> 面向自托管 operator 的一站式运维手册：部署、升级、回滚、认证、备份
> 恢复、成员与池管理、健康检查、故障排查。对应实现：
> `docker-compose.prod.yml`、`docker-compose.allinone.yml`、`./lumirss`
> 生命周期脚本。配置键语义见 [configuration](/configuration)；架构背景见
> [architecture](/architecture)。

## 快速部署（./lumirss）

全新 Ubuntu 22.04/24.04 x86_64 服务器（需 docker engine + compose 插件、
git、curl）：

```bash
git clone https://github.com/paidethon/LumiRSS.git && cd LumiRSS
sudo ./lumirss deploy                # 四容器拓扑（默认）
sudo ./lumirss deploy --single       # 单容器拓扑（见下文）
```

`deploy` 会：preflight（docker/compose/curl、DNS、80/443 占用、磁盘）→
生成并引导填写 `.env.prod`（自动生成 `LUMIRSS_INTERNAL_TOKEN`；交互式
询问域名与登录账号）→ 拉取 GHCR 预构建镜像（**prebuilt-only**：拉取失败
立即中止，旧栈保持运行，绝不回退本地构建）→ `up -d` → 等待
`/health/ready` → 打印 status。

非交互部署（脚本/云-init）：`LUMIRSS_DOMAIN`、`LUMIRSS_AUTH_USER`、
`LUMIRSS_AUTH_HASH`、`LUMIRSS_AUTH_PASSWORD` 环境变量覆盖询问；
`./lumirss deploy --dry-run` 只做配置校验。其它 flags：
`--auth-mode=session`（见[访问控制](#access-control)）、
`--external-caddy`（见[外部反代](#external-caddy)）、`--low-memory`
（低资源预设）。部署后首次登录与邀请成员见
[getting-started](/getting-started#first-login)。

## 生命周期子命令

| 命令 | 作用 |
|---|---|
| `./lumirss update` | 备份（**失败即中止升级**：pull/切流/迁移都不发生，旧栈保持运行）→ 拉取镜像 → `up -d` → 健康检查 |
| `./lumirss status` | 容器状态、健康、web/bff 版本（commit）与镜像 tag |
| `./lumirss logs [service] [-f]` | 全栈或单服务日志 |
| `./lumirss backup` | 一致性卷备份到 `./backups/<stamp>/`（`LUMIRSS_BACKUP_DIR` 可改），见[备份与恢复](#backup-restore) |
| `./lumirss restore <backup.tar.gz> [--yes]` | 停 bff → 覆盖卷 → 校验并回写一致性快照 → 启动 → 健康检查（破坏性，需输入 `RESTORE` 或 `--yes`） |
| `./lumirss doctor` | PASS/WARN/FAIL 诊断（docker、compose、.env.prod、DNS、容器与健康、**OOM/重启计数**、备份就绪 `fullBackupReady`、磁盘、备份目录；external 模式另查公网暴露与 HTTPS；session 模式另查密码已初始化） |
| `./lumirss rollback` | 回到上一镜像 tag + 恢复上一份 `.env.prod` 快照 |
| `./lumirss migrate-single` | 四容器 → 单容器拓扑迁移（见[单容器拓扑](#single-container)） |
| `./lumirss rollback-single` | 单容器 → 迁移前的四容器栈 |
| `./lumirss caddy-config` | 打印宿主 Caddy 站点块（`BEGIN/END LUMIRSS` 管理标记；external 模式用） |
| `./lumirss set-password` | 安装/轮换 owner 登录密码（session 模式）。交互输入或 stdin / `LUMIRSS_NEW_PASSWORD` 运行时秘密；**只把 bcrypt 哈希写进控制库，明文任何地方不落盘** |
| `./lumirss freshrss-init` | 安装/启用内部 FreshRSS 与 BFF 用户（幂等） |
| `./lumirss export-images [--out DIR]` | `docker save` pinned 镜像 → `lumirss-images-<tag>.tar` + `SHA256SUMS`（离线/air-gapped 用） |
| `./lumirss import-images <DIR>` | 校验 `SHA256SUMS`（失败拒载）→ `docker load` |

镜像默认取 GHCR：`ghcr.io/paidethon/lumirss/lumirss-web` / `-bff`，tag 由
`LUMIRSS_IMAGE_TAG` 控制（默认 = 仓库 `VERSION`，可变 `latest` 绝不是
默认）。**生产路径 prebuilt-only**：compose 不含 `build:` 段，
`deploy` / `update --build` 直接拒绝执行；本地构建只属于开发/CI。

CI 每次发布把 image digest 写进 `release-manifest.json`（version、git
SHA、镜像 digest、生成时间）+ `SHA256SUMS`：始终上传为 workflow
artifact，tag 构建时若对应 GitHub Release 已存在则附加（工作流先核验
推广身份：tag commit == 构建 SHA == 镜像 digest）。

### 离线（air-gapped）升级

1. 联网机器：`./lumirss export-images --out ./offline`；
2. 搬运 `offline/` 到目标机：`./lumirss import-images ./offline`；
3. `./lumirss update`：拉取失败时若本地已有镜像会直接使用（不构建），
   否则中止并保留旧栈。

<a id="external-caddy"></a>

## 已有 Host Caddy / 外部反代（external 模式）

服务器上已有 Caddy/nginx 占用公网 80/443 时，**不要**让 LumiRSS 再绑
80/443：

```bash
sudo ./lumirss deploy --external-caddy
```

- `web` 只发布 `127.0.0.1:${LUMIRSS_UPSTREAM_PORT:-18080} -> 80`
  （纯 HTTP、任意 Host；证书、TLS 终结、HTTP→HTTPS 重定向全部由宿主
  反代负责；不要放行该端口到公网）；
- 容器内 Caddy 仍负责 SPA 静态服务、`/api → bff`、应用层安全响应头
  （HSTS/CSP 以这一份为准，宿主反代不要重复设置冲突值）；
- BFF / FreshRSS / RSSHub 照旧只在内部网络；
- 模式持久化在 `.env.prod`（`LUMIRSS_EXTERNAL_CADDY=1`），后续
  `update` / `rollback` / `doctor` / `backup` 自动复用。

把宿主 Caddy 指向 LumiRSS（幂等生成、带管理标记）：

```bash
./lumirss caddy-config
#   # BEGIN LUMIRSS — generated by './lumirss caddy-config'; managed block.
#   <DOMAIN> {
#       reverse_proxy 127.0.0.1:18080
#   }
#   # END LUMIRSS
```

把输出的站点块放进宿主 Caddyfile（标记之间可随时重新生成覆盖；自有
其它站点块放标记**之外**），然后
`caddy validate --config <配置> && systemctl reload caddy`。external
模式下 `./lumirss doctor` 额外检查：web 未发布公网 80/443、上游仅
loopback、公网 HTTPS 可达、`fullBackupReady`。

<a id="single-container"></a>

## 单容器拓扑（all-in-one，可选）

`docker-compose.allinone.yml` 把 **Caddy + FastAPI BFF + FreshRSS
（php-fpm）+ RSSHub** 放进同一个 s6-overlay 监管的容器（GHCR 预构建）。
镜像内部结构见仓库文件 `docker/all-in-one/README.md`（docs 树外）。

```bash
sudo ./lumirss deploy --single        # 全新部署，直接进单容器
sudo ./lumirss migrate-single         # 已有四容器栈 → 单容器
sudo ./lumirss rollback-single        # 单容器 → 迁移前的四容器栈
```

**何时用**：小规格单机（如 1.6 GB 内存 VPS）想少管几个容器。四容器仍是
默认与首选——单容器是**一个 cgroup 装四个负载**：内存隔离变弱（单个
失控服务可 OOM 整个容器；RSSHub V8 堆上限 `LUMIRSS_RSSHUB_NODE_OPTIONS`
是主要约束杠杆），且镜像仅 amd64。空闲实测约 340 MiB（1200m limit）。

- **不变量**：compose 项目名与两个命名卷（`lumi-data`、`freshrss-data`）
  与 uid 模型与四容器栈完全一致——两个拓扑互迁而数据卷原样通用；
  `./lumirss backup` / `restore` 照常工作。
- **形态差异**：单容器天生 external-caddy-only（只发布
  `127.0.0.1:18080 -> 80`，TLS 由宿主反代终结；`--single` 与
  `--external-caddy` 不能组合也不需要）；`LUMIRSS_AUTH_USER/HASH` 被忽略
  并告警——访问控制即应用会话；内部上游地址被 compose 固定为容器内
  loopback。FreshRSS / RSSHub / BFF 端口全部只在容器 loopback。
- **迁移安全链**（每步失败都如实报告真实栈状态）：回退点快照（env 快照
  + 上一镜像 tag + 运行中镜像 ID + 迁移前 schema 版本，在任何改动
  **之前**采集）→ 备份门（失败即中止，什么都不改）→ 拉取门（失败即
  中止，旧栈继续运行）→ `down` 旧栈（**绝不带 `-v`**）→ 起单容器 →
  健康检查 → 版本/镜像自证 → 持久化 `LUMIRSS_SINGLE=1`。
- **回滚**：按回退点逆向恢复四容器栈（卷共享，单容器期间写入的数据都
  保留）；若 schema 已前滚，旧镜像无法撤销迁移——交互需输入 `ROLLBACK`、
  非交互需 `--yes`，更稳妥的替代是恢复迁移前备份。

<a id="access-control"></a>

## 访问控制与边缘安全

两种模式（`LUMIRSS_AUTH_MODE`，`./lumirss deploy --auth-mode=…` 切换）。
**应用会话（session）为主模式**；basic 保留为**兼容可选项**（未显式
设置 `LUMIRSS_AUTH_MODE` 时，env 缺省仍是 `basic`）。

### session 模式（推荐：账号登录，长效会话）

```bash
sudo ./lumirss deploy --auth-mode=session
sudo ./lumirss set-password          # 安装/轮换 owner 密码
```

- **登录流**：浏览器提交 `{username, password}` → BFF bcrypt 校验（哈希
  只存控制库，明文任何地方不落盘）→ 签发 256-bit 随机 opaque session
  （数据库只存其 SHA-256）→ `__Host-lumirss_session` Cookie
  （`Secure; HttpOnly; SameSite=Strict; Path=/`，无 `Domain`）。
- **长期有效**：默认 180 天不活跃窗口（`LUMIRSS_SESSION_MAX_AGE_DAYS`），
  活跃使用自动滑动续期。改密 → 撤销该账号全部会话（本设备自动换发）；
  登出/所有设备登出在「设置 → 账户与服务」。
- **防护**：登录失败限流（5 次失败/分钟 → 429，成功即重置，不锁账户）；
  不安全方法做 Origin 同源校验（CSRF）；会话表有界（过期行登录时清理 +
  每账号最多 20 个活跃会话）。
- **边界**：静态资源与 `/api/v1/auth/*`、`/health/*`、`/api/v1/version`
  公开；其余 `/api/*` 需要会话。internal token 层照常生效（会话不替代
  internal token——后者防的是绕过 Caddy 直连 BFF）。
- 从 basic 切换：重新 deploy 带 `--auth-mode=session` 并执行
  `set-password`；回退同理（`--auth-mode=basic` + 原 USER/HASH 仍在）。

### basic 模式（兼容可选项）

`LUMIRSS_AUTH_USER` + `LUMIRSS_AUTH_HASH` 都设置 → Caddy basic_auth
（bcrypt）；都为空 → 无 auth（受信内网/已有外层认证）。**只设一个容器
拒绝启动**（防止半配置静默关闭访问控制）。单容器拓扑下这两个变量被忽略。

### 通用

- **TLS 三态**：真实域名 → Let's Encrypt；`localhost` → 自签 + 强制
  HTTPS；`http://:80` 形式 → 纯 HTTP（仅内网调试）。
- **BFF internal token（可选但推荐）**：`.env.prod` 设置
  `LUMIRSS_INTERNAL_TOKEN` 后，BFF 拒绝一切不带匹配 `X-Lumi-Token` 头的
  `/api/*` 请求（401；`/health/*` 豁免）。两个容器读同一份 `.env.prod`，
  要么都设要么都不设。
- **安全响应头**：nosniff / X-Frame-Options DENY / no-referrer / HSTS /
  Permissions-Policy / CSP（`script-src 'self'` + 内联主题脚本 sha256
  pin——修改 `apps/web/index.html` 内联脚本时必须同步更新两个 Caddyfile
  的哈希，漂移会被 `apps/web/src/__tests__/csp-hash.test.ts` 捕获）；
  `style-src` 保留 `unsafe-inline`；`img-src`/`media-src` 允许远端；
  `frame-ancestors 'none'`。
- **BFF 侧硬化**：全局请求体 4 MiB 上限（超限 → 413
  `request_too_large`；OPML 导入更严格 2 MiB）；昂贵控制面路由进程内
  固定窗口限流（超限 → 429 `rate_limited` + `Retry-After`：restore
  10/min、backups 12/min、feed 预览/来源发现 30/min、AI/MT 生成 120/min、
  RSSHub 变更 60/min；阅读类 GET 不限流）。

## 升级与回滚

```bash
./lumirss update        # 备份（失败即中止，旧栈保持运行）→ 拉取 → up → 健康检查（推荐）
```

手工等价：确认容器健康 → 在 UI 创建完整备份 →
`git pull && git checkout <release-tag>` →
`docker compose -f docker-compose.prod.yml pull && up -d` → 就绪检查。

拉取失败时 `update` 直接中止，旧栈继续运行。绝不本地构建替代线上镜像。

回滚：`./lumirss rollback`（上一镜像 tag + 上一份配置快照）。SQLite
schema 不做二进制降级；数据库不兼容时唯一受支持路径是恢复升级前备份。
**2.0.0 起数据布局改变（控制库 + 每用户库），跨该版本回退只能恢复升级前
备份**。

### iOS 客户端的服务器兼容升级

iOS 客户端通过 `GET /api/v1/version` 探测服务器，要求 ≥ 3.0.0。服务器
正常按上述 `./lumirss update` 流程升级即可——原生客户端不引入新端点，
升级后 App 重启（或重新登录）即可继续使用；服务器降级到 3.0.0 以下时
App 会在连接页明确提示版本不兼容，Web 不受影响。

### iOS 客户端获取与安装（IPA）

当前阶段（0.1.0 Preview）：CI 只产出**未签名**的设备归档
（GitHub Actions `iOS` workflow → artifact
`ios-unsigned-devpreview-<sha>`，含 SHA256SUMS）——它是开发预览，
**不能直接安装到 iPhone**。可安装的签名 IPA 需要运营者补齐 Apple
开发者配置（Secrets 清单与启用步骤见
[development](/development) §iOS 签名）；具备 Ad Hoc 条件后，同一
workflow 会输出带 profile 的安装包并附设备 UDID 说明。模拟器构建
产物（`ios-build-test-<sha>` artifact 中的截图/日志）仅作验证证据。

## 备份与恢复

两条路径：

1. **UI / API（应用级，功能最全）**：设置 →「数据控制」（配置迁移 /
   完整备份 / 备份历史 / WebDAV / 恢复同页）。
2. **`./lumirss backup` / `restore`（卷级，整机运维）**：一致性卷备份到
   `./backups/<stamp>/`。

### 卷级备份布局

```text
$BACKUP_DIR/<stamp>/            # 撞名自动退避为 <stamp>-<pid>
  MANIFEST.txt                  # 每个快照库的 sha256 + 体积 + CLI 版本
  lumi-sqlite/…                 # 控制库 + users/<uid>/lumi.sqlite 的一致性快照
  freshrss-sqlite/…             # FreshRSS db.sqlite 的一致性快照
  lumi-data.files.tar.gz        # 非 DB 文件 file-level tar（*.sqlite 与
  freshrss-data.files.tar.gz    #   -wal/-shm/-journal 边车一律排除）
  config.tar.gz                 # .env.prod + docker-compose.prod.yml
$BACKUP_DIR/LATEST              # 最近一次完整成功的 stamp 名（原子 mv）
```

一致性边界（诚实声明）：

- **数据库走 SQLite online backup API 快照**：所有页来自**同一个 WAL
  读点**——绝不出现裸 tar 活库的缺页/撕裂。恢复时先整目录校验
  `MANIFEST.txt` 的 sha256，再按相对路径覆盖回卷。
- **其余文件**（secrets、FreshRSS `config.php` 等）为 file-level tar：
  低频写且本身容错。
- **备份容器镜像**默认 = 栈自身的 BFF 镜像（离线主机零额外拉取）；
  `LUMIRSS_BACKUP_IMAGE` 可覆盖，但覆盖镜像**必须提供 python3 + tar**，
  缺失时备份如实失败并整目录回滚。
- `./lumirss update` 的第一阶段就是备份：**备份失败即中止升级**。

### 敏感性

- **备份必须当作敏感文件保管**：Lumi 自身的秘密值（AI/WebDAV/RSSHub/
  FreshRSS API 密码、auth 哈希）**不进备份**，恢复后需重新配置；但
  **FreshRSS 数据目录本身可能含凭据敏感材料**。切勿把备份归档提交到
  Git 或上传到不受信位置。
- 存储：本机 `data/backups/` 限制文件系统权限；WebDAV 传输走 TLS
  （http 仅允许私网/回环），远端目录需访问控制。密码 write-only 永不
  回显；`GET /api/v1/backups/remote` 列出远端备份。

### 完整备份能力预检与 FreshRSS 权限边界

`GET /api/v1/backups/capabilities` 在点击前如实回答"完整备份现在能包含
什么"（FreshRSS 数据目录是否可读、外部 MySQL/PostgreSQL 明确拒绝、
组件清单）。FreshRSS 把 `data/users/<user>/` 建为 `0770 root:www-data`：

- **生产 Compose**：`docker-compose.prod.yml` 已给 BFF 容器
  `group_add: ["33"]`（www-data 组），BFF（uid 10001）可只读遍历。旧部署
  升级后需 `up -d --force-recreate bff` 生效。
- **开发栈**：完整备份需一次性迁移到 bind mount（见
  `docker-compose.dev-backup.yml` 头注释），并执行一次
  `docker exec freshrss sh -c 'chmod -R a+rX /var/www/FreshRSS/data'`；
  BFF 侧在 `services/bff/.env` 设 `FRESHRSS_DATA_DIR` 指向同一目录。
- 预检/执行对"目录存在但部分不可读"一律诚实失败
  （`unreadable_entries`），绝不产出缺用户数据库的"假完整包"。

### 恢复

- 单并发 job；阶段真实上报；**恢复前自动创建当前状态安全备份**；损坏
  checksum / 不兼容版本会被拒绝；需显式输入 `RESTORE`。
- FreshRSS 数据恢复为**离线恢复**：文件就绪于
  `data/restore-staging/restore-ready/freshrss/`，operator 按官方 compose
  步骤自行覆盖 FreshRSS 卷（Lumi 不写运行中的 FreshRSS）。
- 恢复后残留的 interrupted 记录是正常审计。

### 灾难恢复流程

1. 部署全新栈（本文[快速部署](#快速部署lumirss)或 external 模式）；
2. 取回最近备份（本机卷或 WebDAV）；
3. 「数据控制 → 备份历史 → 从此备份恢复」→ 预览校验 → 输入 `RESTORE`；
4. FreshRSS 数据按上文离线恢复；`/health/ready` + 阅读流程验证。

### 磁盘维护

`data/backups/` 与 `data/restore-staging/` 定期清理（staging 会话与
24h 前下载会自动清理）。

## 成员、邀请与 FreshRSS 池（运营者）

LumiRSS 默认邀请制多账户。管理界面 `/admin`（仅 owner/admin 角色可见；
权限由服务端核实，前端隐藏入口只是体验优化）。

### 发出邀请

1. `/admin` → 邀请（或 `POST /api/v1/admin/invites`）；
2. 设置有效期（默认 72 小时，上限 30 天）与可选备注；
3. 系统返回一次性邀请链接（`/activate?token=…`）。**原始 token 只显示
   一次**——数据库只存其 SHA-256，只能作废重发；
4. 把链接私下交给受邀者。未使用的邀请可随时撤销。

激活流程（受邀者视角）见 [getting-started](/getting-started#activate)。

### 准备 FreshRSS 账号池（激活前做）

每个账号的 RSS 真源是它自己的 FreshRSS 账号。运营者用
`scripts/freshrss_pool.sh` 预建空账号并登记进 Lumi 池：

```bash
FRESHRSS_ADMIN_PASSWORD=… LUMI_ADMIN_PASSWORD=… \
scripts/freshrss_pool.sh 3 http://freshrss admin http://127.0.0.1:8000
```

- 激活时 BFF **原子分配**——两个并发激活不可能拿到同一账号；
- **池空 ≠ 不能用**：账号照常激活，RSS 绑定显示「待就绪」，之后补池即可；
- 全程没有共享凭据回退；API 密码只存部署侧 secrets 文件（0600），不入库；
- 池状态在 `/admin`（或 `GET /api/v1/admin/pool`）可见：ready / assigned。

### 暂停 / 恢复成员

`/admin` → 成员列表（或 `POST /api/v1/admin/users/{id}/pause` / `/resume`）：
暂停立即拒绝新登录并失效已有会话（数据保留）；恢复后一切原样。运营者
本人（owner）不可被暂停；需要收回权限时改用重置密码。

### 重置成员密码

`/admin` → 成员 → 重置密码（或 `POST /api/v1/admin/users/{id}/reset-password`）：
安装无人知晓的随机密码并撤销全部会话 → 返回 24 小时有效的**恢复邀请**
（原始 token 只显示一次）→ 成员在 `/activate` 自设新密码。没有邮件发送
环节——链接由运营者亲手转交。

### 公开注册策略（可选，默认关闭）

开关存控制库（`allow_public_registration`），不是 env；`GET/PUT
/api/v1/admin/registration-policy`（admin 会话）显式切换，变更落审计。
开启后注册只创建 member、限流 10 次/60 秒并纳入 CSRF Origin 校验；关闭
时统一 403 `registration_disabled`。是否在公网实例开启由运营者自行评估
暴露面。背景与语义见 [architecture](/architecture#accounts)。

<a id="health-logs"></a>

## 健康检查与日志

- 容器 HEALTHCHECK：`bff` 探测 `GET /health/live`；`web` 探测容器内部
  `:9137/index.html`（同时校验响应体含 Vite 构建的 `/assets/` 引用）。
  `docker compose ps` 的 healthy 状态即来自这两项。
- `GET /health/live` — 进程存活（仅容器内）。
- `GET /health/ready` — 核心依赖（lumi.sqlite）不可用才 503；
  FreshRSS/RSSHub 故障不影响 readiness（失败隔离）。
- `GET /api/v1/operations/status` — 各依赖真实探测（延迟/类型化错误），
  经 Caddy 对外可达；UI 在「设置 → 服务」展示。
- 日志：`json-file` 轮转（10 MB × 3）；`./lumirss logs bff` 查看；
  错误消息为脱敏安全文本。BFF 访问日志每请求一行结构化 JSON
  （request_id/路由/status/耗时/服务端 actor），绝不记录 query string /
  请求体 / header；`LUMIRSS_ACCESS_LOG=off` 可静默（默认 `json`）。

## 手工部署（等价路径）

```bash
cp .env.prod.example .env.prod   # 填写真实值；$ 必须写成 $$（见 configuration）
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

- 唯一公网入口是 `web`（Caddy，80/443）；BFF **不发布任何宿主端口**。
- FreshRSS / RSSHub 镜像按 digest/版本 pin（不随系统升级漂移）。
- 最低资源：2 vCPU / 2 GB RAM / 10 GB 磁盘（RSSHub 峰值内存最高）。
  小内存 VPS 用 `./lumirss deploy --low-memory` 写入低资源预设（web 96m /
  bff 256m / freshrss 320m / rsshub 448m + RSSHub memory cache 64 MB +
  V8 堆 256 MB）。改完用 `./lumirss doctor` 验证：任何 OOMKilled = limit
  过低，调大对应 `LUMIRSS_*_MEM_LIMIT`，绝不把 OOM 交付为"更低占用"。

就绪检查（从容器内执行）：

```bash
docker compose -f docker-compose.prod.yml exec bff \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=5).status)"
```

> 在同一台机器上测试而不影响正式栈：设置独立的 `LUMIRSS_HTTP_PORT` /
> `LUMIRSS_HTTPS_PORT` / `COMPOSE_PROJECT_NAME` 再部署（见
> [configuration](/configuration)）。

<a id="troubleshooting"></a>

## 故障排查

排查入口：`./lumirss doctor` 与 `./lumirss status`；日志
`./lumirss logs [service]`。应用内维护工具（脱敏诊断包、操作记录、会话
管理、派生数据保留、回收站、设置历史）在「设置」中心。

| 症状 | 处置 |
|---|---|
| **RSS 永不自动更新**（只有手动刷新才出现新文章） | ① 上游 feed 是否真有新条目；② FreshRSS 容器是否设置了 `CRON_MIN`——缺省时容器内置 cron 不启动，订阅永不自动刷新。修复：compose 的 freshrss 加 `CRON_MIN: "13,43"` 并 `docker compose up -d freshrss`；验证 `docker exec <freshrss容器> cat /var/spool/cron/crontabs/*` 有 actualize 行；③ 投影滞后：`GET /api/v1/sources/volume` 看 lastSyncedAt 是否推进 |
| 界面新功能调用接口返回 404 | 线上 BFF 是旧镜像：`./lumirss status` 看 image tag → `LUMIRSS_IMAGE_TAG=<新tag> ./lumirss update`。生产是 prebuilt-only，`--build` 会被拒绝 |
| 容器反复重启、auth 不生效 | `.env.prod` auth 只设了一个变量（entrypoint FATAL）或 bcrypt `$` 未转义 `$$`（见 [configuration](/configuration)） |
| FreshRSS unhealthy → BFF 不启动 | healthcheck = 官方 `php cli/health.php`；确认 FreshRSS 初始化完成（首次安装需先完成安装向导） |
| RSSHub 不可用 | 只影响来源发现/预览；阅读不受影响；`docker compose restart rsshub` |
| 设置 `LUMIRSS_INTERNAL_TOKEN` 后 API 全 401 | 直连 BFF 的调用必须带 `X-Lumi-Token` 头；两个容器读同一份 `.env.prod`，只设一侧会导致全 401 或无效果 |
| 完整备份报 `unreadable_entries` | FreshRSS 用户目录权限（0770 root:www-data）；处置见[权限边界](#backup-restore) |
| 恢复后残留 interrupted 记录 | 正常：恢复会把快照中的陈旧运行态标记为 interrupted（审计） |
| 磁盘增长 | 清理 `data/backups/` 与 `data/restore-staging/` |
| 部署时 DNS/端口告警 | preflight 会告警域名未解析、80/443 被占用、磁盘不足；先解决再部署 |
| 机器推送（收件箱 ingest / 邮件 webhook）在 session 模式下 401 | 这两条是机器到机器端点（bearer 鉴权），外层 host Caddy 若开了 basic auth 会先拦截：在 host 反代上对 `/api/v1/inbox/ingest/*` 与 `/api/mail/ingest/*` 放行（仍受 BFF 侧 bearer 保护） |
| 成员账号 RSS 绑定显示「待就绪」 | 激活时 FreshRSS 账号池为空（诚实状态）：运营者补池即可（见[池](#member-admin)） |
| 成员登录返回 401 且确认密码正确 | 账号可能被暂停（`/admin` → 成员 → 恢复）或邀请/恢复链接已过期（一次性限时，过期后请运营者重发）；owner 密码遗忘用 `./lumirss set-password` |
| 回滚到旧镜像后邮件桥报错 | 回退跨越 0018（`mail_seen` 重建）之前的镜像时，须先把 DB 回滚到对应 schema 版本的快照；跨 2.0.0 回退只能恢复升级前备份（见[升级与回滚](#升级与回滚)） |
